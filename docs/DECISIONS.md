# Engineering Decisions

A running log of the non-obvious choices made building this repo, and why. Design/architecture reasoning lives in [`docs/design/DESIGN-V3.md`](./design/DESIGN-V3.md). This log covers the choices that had a real rejected alternative worth recording.

## Language

**Python for the whole pipeline (Extract, Transform, Load), not TypeScript.** TypeScript was the original draft assumption, made before Extract's real requirements were worked out. The team reversed this once it became clear Extract carries the pipeline's actual complexity and compute cost: OCR, vision-LLM calls, per-vendor adapters. Python's OCR/ML ecosystem is native and mature there — EasyOCR, PaddleOCR, docTR, and `pytesseract` all run in-process. The TypeScript equivalents are thin or nonexistent and would need a separate Python service anyway. Once Extract needs Python, keeping Transform and Load in the same language avoids a cross-language boundary for stages that don't need one. Neither stage has any real technical pull toward TypeScript.

## Tooling

**`gen:types` runs `datamodel-codegen` with `--use-annotated`, not its default `confloat`/`constr`-style output.** By default, `datamodel-codegen`'s `pydantic_v2.BaseModel` output uses Pydantic's `confloat(ge=0.0, le=1.0)`-style wrapper functions for constrained fields (e.g. `ExtractionReview.confidence_score`). Pydantic's own docs mark these as discouraged, headed for deprecation in Pydantic 3.0, since a function that returns a type doesn't play well with static analysis. `datamodel-codegen` (confirmed on the installed 0.80.0) already supports `--use-annotated` (which also enables `--field-constraints`), producing Pydantic's own recommended `Annotated[float, Field(ge=0.0, le=1.0)]` form instead. Added to `gen:types` in `pyproject.toml` so every regeneration — including the standing per-session submodule-pin-update flow — stays on the non-deprecated pattern going forward, rather than waiting for the warning to become a hard break.

## Architecture

**No direct database connection to `vela-core`, ever.** Originally the team assumed `vela-etl` would connect directly to Postgres. `vela-core` looked like schema and migrations only, not a running service. The team reversed this once the platform's write-path rule became explicit. `vela-api` is the only service with a direct connection to `vela-core`. `vela-etl` has no DB driver and no DB credentials. It calls `vela-api` over HTTP instead.

**Contract with `vela-api` is two separate things: data shape (JSON Schema) and endpoint shape (OpenAPI).** The team considered generating types from an OpenAPI spec directly. This is the way a typical REST client generator would work. Rejected. The data types already come from `vela-core`'s JSON Schema via `datamodel-code-generator`, independent of anything `vela-api` does. An OpenAPI spec, if `vela-api` ever publishes one, only ever describes the URL, method, and wrapper around that same data. There is nothing left for a second code-generation step to produce. This also means `vela-etl` never needs to know or mirror any tooling choice made on `vela-api`'s side.

**`vela-api`'s write contract: one combined-payload endpoint, not per-table endpoints.** The team considered `POST /receipts`, `POST /line-items`, and `POST /extraction-reviews` as three separate calls, more conventionally REST-ish. Rejected in favor of a single POST carrying the whole shaped receipt with nested line_items and reviews, written atomically. Reasoning: `vela-etl`'s Emit step already bundles all three into one unit. Per-table endpoints would mean re-splitting output on the way out for no benefit. Per-table calls also risk partial-write states — receipt written, line_items call fails, review call never happens — that a combined endpoint avoids by construction. This is `vela-etl`'s stated expectation handed to `vela-api`, not a guarantee of `vela-api`'s actual implementation.

**Both `vela-etl` and `vela-api` validate against `vela-core`'s JSON Schema — not just one side.** The team considered leaving validation to `vela-api` alone. It is the actual enforcement point and the single source of truth either way. Rejected purity for practicality. `vela-etl` validates first, so a malformed payload fails fast with a useful local error during development, before a request ever leaves the pipeline. `vela-api` re-validates on receipt regardless, since it can't fully trust every caller, especially once other clients might exist. `vela-etl`'s check is an optimization, never the enforcement mechanism.

## Privacy

**No anonymization or redaction: confirmed, not left open.** v1 flagged two fields as needing confirmation: `receipts.customer_name` and `extras`. They needed to never hold a third party's personal data. Confirmed: this is a local project processing only the project owner's own receipts, with no third-party exposure path. The decision stands as data minimization, meaning extract only what the schema defines, rather than redaction. This is consistent with the platform-wide privacy principle. If the team ever needs reversible redaction, field-level (not whole-row) encryption is the fallback design. The key stays separate from the data. Decryption is a permissioned, logged action.

## Extraction

**Extractors are a plain list behind one shared interface, not a "one extractor vs. many, with a special fallback case" branch.** The team considered a different model: a primary extractor plus an explicit fallback path. If the primary extractor is low-confidence, it would call a named backup. Rejected. Reconciliation only ever sees a results list of length 1 or N. It never knows or asks how many extractors ran, or why. This makes "run two extractors always" and "run one, conditionally fall back to a second" the exact same code path downstream. Adding a new vendor is purely additive, meaning one adapter and one config entry, with zero changes to orchestration or reconciliation.

**Total-failure `ExtractionReview` shape: resolved upstream in `vela-core` commit `1619173`.** DESIGN-V3.md line 87 says a total extraction failure (illegible image, API error — no candidate produced at all) returns an `ExtractionReview`-shaped row directly, citing `flagged_reason: "illegible"` as the example. That example didn't hold up against `vela-core`'s actual contract at the time: `field_name` only documented three cases (a real column name, `"line_item"`, `"missing_line_item"`), none fitting "nothing was extracted at all," and `illegible` itself was shown by `vela-core`'s seed data to mean "one field/character couldn't be read," not "the whole receipt failed." `vela-etl` used `field_name="receipt"` as a provisional local placeholder while this was raised with `vela-core` (handover: `docs/work/vela-core-handover-total-failure-sentinel.md`).

`vela-core` resolved it in `1619173` (`feat(schema): add extraction_failed sentinel for total extraction failures`): a fourth `field_name` sentinel, `"receipt"`, paired with a new `flagged_reason` enum value, `"extraction_failed"` — always used together, so the case is detectable on either field alone. `line_item_id`/`extracted_value` stay null, matching the existing `"missing_line_item"` pattern. `vela-etl`'s submodule pin was bumped to `1619173` and types regenerated (`uv run poe submodule:update` + `gen:types`); `tests/test_orchestrator.py`'s `_TotalFailureExtractor` now constructs `field_name="receipt"` + `flagged_reason=FlaggedReason.extraction_failed` as the real, schema-backed case, not a placeholder.

## Transform

**`shape()`'s extras split: introspect `Receipt.model_fields` at runtime, not a hardcoded field list.** The team considered writing out an explicit set of recognized column names directly in `shape.py`, independent of the generated `Receipt` model. Rejected. `Receipt` is generated from `vela-core`'s vendored JSON Schema via `datamodel-code-generator` (`uv run poe gen:types`); a hardcoded list would silently drift out of sync the next time that schema changes and types are regenerated, requiring a second manual edit nobody is guaranteed to remember. Introspecting `Receipt.model_fields` at runtime means any resolved key matching a real field name on the generated model becomes a column, and everything else — by definition, anything the schema doesn't recognize — goes into `Receipt.extras`. A schema change plus a `gen:types` regen is picked up automatically with zero code changes in `shape.py`. `LineItem` and `Store` need no equivalent split: neither has an `extras` field in the schema, and their candidate types (`CandidateLineItem`/`CandidateStore`) only ever define real schema fields in the first place.

**`validate()`'s derived confidence score scales with the size of the arithmetic mismatch, not a flat value.** An early version gave every self-caught inconsistency (e.g. `quantity * unit_price != line_total`) the same fixed `confidence_score=0.0`. The team rejected this on review: a total off by a rounding-sized amount (1%) is a meaningfully different signal than one off by 50%+, and collapsing both to the same score throws that signal away. `validate()` now computes a relative error (`abs(actual - expected) / denominator`) and maps it to `1.0 - relative_error`, floored at `0.0` and capped at `0.99` (a flagged row can approach but never reach full confidence). A missing required field has no "how far off" to measure, so it keeps the flat `0.0` — the scaling only applies to arithmetic mismatches, which are the only case with a meaningful distance to measure. **Follow-up fix, same review round**: the initial version divided by `expected` directly, which meant a small absolute gap on a small total (e.g. total=1.00, off by 0.05) computed as a huge relative error (95%) and clamped to the same 0.0 score as a receipt that was wildly, unambiguously wrong — indistinguishable even though the absolute gap was currency-scale trivial. A first fix floored the denominator at a hardcoded `10.0`, but that number itself baked in a currency/magnitude assumption (what counts as "small" varies by currency and receipt scale) with no real basis. **Final fix**: the formula no longer reasons about the receipt's total's scale at all. An absolute gap within `_NEGLIGIBLE_GAP_MULTIPLE` (5) multiples of `_TOLERANCE` (the same 0.01 unit already used for the pass/fail arithmetic check) is treated as negligible and scores `0.99`, regardless of `expected`'s size; only once the gap exceeds that does relative error kick in to further degrade the score. This ties "what counts as a small gap" to the same currency-unit-agnostic tolerance already defined in the file, instead of an arbitrary absolute floor.

**`reconcile()` matches line items across extractors one item at a time against open groups, not by a precomputed `(description, occurrence)` key.** Two versions preceded this one, both with real bugs caught on review. First version: grouped purely by normalized description, so the same product listed twice on one receipt (e.g. two "Coca-Cola 500ml" lines) had its second occurrence silently overwrite the first — a real correctness bug, not just a documented limitation. Second version: fixed that by keying groups on `(normalized_description, occurrence_index)`, counting each extractor's Nth occurrence of an exact description string. This introduced a subtler bug: occurrence-counting was keyed by *exact* string, so if one extractor spelled a duplicate item's two occurrences inconsistently (e.g. "Paracetamol" then "Paracetmol", a typo on the second), the two occurrences were treated as two entirely different description keys with independent occurrence counters, breaking the correspondence between extractors' Nth occurrences. **Current version**: each item is assigned to a group one at a time by finding the best still-open group (a group this extractor hasn't already filled) — exact normalized-description match preferred, fuzzy match as fallback, new group only if neither exists. This makes matching correct regardless of *why* one extractor's two occurrences of the same item look different (typo, or a real duplicate with no typo at all), since group assignment is driven by "is there a compatible open group," not by a description string used as a literal dictionary key.

**`reconcile()` falls back to fuzzy description matching (via stdlib `difflib.SequenceMatcher`) for line items that don't match exactly.** Exact-match-only matching (after case/whitespace normalization) doesn't tolerate small OCR-style typos between extractors (e.g. "Paracetmol 500mg" vs "Paracetamol 500mg"), which would otherwise be treated as two entirely different items rather than one item with a field-level disagreement. Confirmed with user: added a conservative similarity threshold (`_DESCRIPTION_SIMILARITY_THRESHOLD = 0.9`), high enough that short, genuinely different words (e.g. "Milk" vs "Mild", one character apart but different products) stay below it and are never merged, while still catching small single-character-class differences. Fuzzy matching only ever applies as a fallback when no exact-match open group exists, and never lets one extractor fill more than one slot in the same group (see the group-matching entry above for how this composes correctly with duplicate items). This is still an approximation — no semantic understanding of product names — and is documented as such, not treated as a complete solution to real-world OCR noise.

**A single-extractor line item, among 2+ total extractors, gets a `low_confidence` flag on top of the `missing_line_item` rows it already earns.** Previously an item produced by only one extractor out of several was accepted into `resolved_items` with no review flag at all, even though the other extractors' absence already produces `missing_line_item` rows for them — the item's own existence is disputed, but its field values were trusted the same as an item every present extractor agreed on. Fixed: when more than one extractor ran in total and only one produced this item, a `flagged_reason="low_confidence"` row is added (`field_name="line_item"`, reusing the same sentinel the design doc defines for "the whole item is wrong" since this is a closely related but distinct case — "unconfirmed," not necessarily wrong). This does **not** apply when there was only ever one extractor total, which is the ordinary, ever-present single-extractor pass-through case with nothing to be disputed against.

**Missing/present extractor accounting in `_reconcile_line_items` is keyed by list index, never by `extractor_source` name.** An earlier version built a `set` of `source` strings to determine which extractors were present vs. absent for a given line-item group. This silently breaks if two `ExtractionResult`s in the list share the same `source` name (e.g. the same extractor run twice) — the set collapses them into one entry, so an extractor that genuinely produced nothing could be masked by another entry with the same name that did. Fixed by tracking `result_index` (the position in the `results` list, always unique) throughout, and only resolving to the `source` string at the point of constructing each `ExtractionReview` row.

**`shape()` constructs `Receipt` before computing `content_hash` from its fields, not the other way around.** The original order computed `content_hash` from `columns.get(...)`-derived raw dict values first, then constructed `Receipt` afterward. If a required field was missing from `columns` (e.g. left unresolved by `reconcile()`), the hash function received `None` and silently hashed the literal string `"None"` — computing a valid-looking hash for a receipt that was about to fail construction anyway, rather than raising immediately. Fixed by constructing `Receipt` first (with an empty placeholder `content_hash`) so pydantic's required-field validation runs and raises before any hashing happens, then computing the real hash from the now-validated `receipt` instance's own fields and assigning it.

**`reconcile()` raises rather than silently truncating when `Candidate.line_items` and `Confidence.line_items` have mismatched lengths.** `Confidence.line_items` is documented (in `extract/types.py`) as positionally aligned with `Candidate.line_items`, but `ExtractionResult`'s own construction never enforces the two lists are the same length. An earlier version zipped them with `strict=False`, which would silently drop a real line item from reconciliation entirely — no error, no review row, just gone — if a malformed `ExtractionResult` ever had mismatched lengths (e.g. an orchestrator/extractor bug). Fixed: `_group_line_items_by_description` now explicitly checks the lengths per extractor and raises `ValueError` with a clear message identifying the offending `source` before zipping, rather than trusting `zip`'s silent-truncation default. A length mismatch signals the `ExtractionResult` itself was built incorrectly upstream — `reconcile()` should never paper over that.

**`shape()`'s extras split matches resolved keys against declared field aliases as well as attribute names, not attribute names alone.** `Receipt.model_fields` gives Python attribute names; it does not automatically include any alias a field might declare (e.g. if `datamodel-code-generator` ever regenerates `Receipt` with a camelCase JSON alias mapped to a snake_case attribute, which `vela-core`'s JSON Schema could introduce at any future regen). Matching attribute names alone would then silently misroute an alias-spelled resolved key into `extras` instead of the real column, with no error — a correctness gap that would only surface once such an alias actually existed, by which point the wrong-routing would already be happening silently. Fixed defensively: the known-fields set now also includes each field's `info.alias` and `info.validation_alias` when declared. `Receipt` declares no aliases today, so this has no behavioral effect on the current schema, but the routing stays correct without a code change if that changes on a future regen.

**Verified non-issue, external review**: a claimed type-coercion risk in `validate()`'s arithmetic checks (`quantity * unit_price`, assuming numeric types without a coercion guard) was checked against the actual data flow and does not hold. Every value `validate()` operates on originates from `reconcile()`'s output, which in turn always comes from a `CandidateLineItem` instance (`quantity`/`unit_price`/`line_total` typed `float` in `extract/types.py`) — either via `.model_dump()` (single-extractor items) or `getattr()` on the same typed instance (per-field-reconciled items). No path introduces a raw, unvalidated string into `resolved["line_items"]`. No fix applied; documented here so the finding isn't silently dropped without explanation.

**`shape()` filters `id`/`receipt_id`/`line_order` out of `item_fields` before constructing each `LineItem`, instead of trusting `CandidateLineItem` will never produce those keys.** `reconcile()`'s single-extractor pass-through path (`resolved_items.append(item.model_dump())`) dumps the full `CandidateLineItem` model, not just the fields `shape()` expects to spread. `CandidateLineItem` doesn't declare `id`/`receipt_id`/`line_order` today, so `LineItem(id=..., receipt_id=..., line_order=index, **item_fields)` can't collide currently — but that safety depended entirely on an assumption about a type `shape()` doesn't own and doesn't control (Phase 2's `CandidateLineItem`, still evolving). If that schema is ever extended to include one of those names — plausible, since `LineItem` itself has all three — the unfiltered spread would raise `TypeError: got multiple values for keyword argument` on every affected receipt, with no warning beforehand. Fixed the same way as the receipt-level known-fields split: explicitly exclude `{"id", "receipt_id", "line_order"}` from `item_fields` before spreading, so `shape()`'s own explicit assignments always win regardless of what `item_fields` happens to contain. `LineItem` has no `extras` field to route excess keys into (unlike `Receipt`), so filtering (not redirecting) is the only option here.

**`validate()` flags a receipt that resolves to a nonzero total with zero line items.** The sum-check (`line items total == receipt total`) previously skipped entirely when `line_items` was empty, since there was nothing to sum — but a receipt with a real total and zero items is almost certainly a total extraction failure (every item was missed), not a legitimately empty receipt, and deserves a review row. Fixed: an empty `line_items` list with a nonzero `total` now produces a `field_name="missing_line_item"` validation-failure row. A `total` of `0.0` (a genuinely zero-value/voided transaction) is not flagged, since that combination isn't inherently suspicious.

**Transform's validator: pydantic only, not `jsonschema` as well.** The design doc's tool inventory lists `pydantic` or `jsonschema` for validating against `vela-core`'s JSON Schema, with both allowed if documented why. The team considered running `jsonschema` against the vendored `.schema.json` files directly, on top of pydantic, as a literal belt-and-suspenders check. Rejected as redundant. The generated types (`src/etl/types/*_schema.py`) are produced directly from those same vendored schema files by `datamodel-code-generator` — constructing a `Receipt`/`LineItem`/`Store`/`ExtractionReview` instance from shaped data already enforces the schema's required fields, types, and constraints, since the model literally is that schema's Python representation. Running `jsonschema` against the same source files a second time would duplicate the exact same check through a second code path, with no independent guarantee gained, since both readers trace back to one source of truth. `shape()`'s construction of `Store`/`Receipt`/`LineItem` is therefore documented as the pre-Load re-validation step, not a separate stage.

**`shape()` requires fully-resolved input; it does not check for unresolved conflicts itself.** The team considered having `shape()` defensively check `reconcile()`'s review list for unresolved receipt/store-level conflicts before building `Store`/`Receipt`/`LineItem`, and skip or fail gracefully if any exist. Rejected for `shape()` itself. `shape()` stays a pure function that trusts its input is already resolved, matching the design doc's stated pipeline order (`reconcile → validate → shape → emit`) — checking for conflicts is `reconcile()`'s own output (the review list), not something `shape()` should re-derive. Confirmed by testing: feeding `shape()` a receipt where `reconcile()` left a required field (e.g. `total`) unresolved due to extractor disagreement causes pydantic to raise `ValidationError` when constructing `Receipt`, since the field is simply missing from the resolved dict. This is treated as correct, not a gap to patch inside `shape()` — a receipt with a disagreed-upon required field must never reach Load. The gap that does need closing is in the caller: **Phase 6's end-to-end wiring must check `reconcile()`'s review list for unresolved receipt/store-level conflicts before calling `shape()`**, and route that receipt to manual review instead of calling `shape()` and catching the resulting error.

**`reconcile()` never infers "the whole line item is wrong" (`field_name="line_item"` sentinel) from how many fields mismatch.** An early version guessed this: if 2+ fields disagreed on the same aligned line item across extractors, it collapsed those into one `field_name="line_item"` row instead of several per-field rows. The team rejected this on review — it was an invented threshold with no basis in the design doc, and it hides which specific fields disagreed from whoever resolves the review. `reconcile()` now only ever emits per-field rows for line-item disagreements, same as receipt/store-level fields. `field_name="line_item"` (whole item wrong) and `field_name="missing_line_item"` (item missed entirely) stay real cases, per `CLAUDE.md`'s "shared data contract" rules, but `reconcile()` does not try to detect "whole item wrong" on its own — it is out of scope for Transform until a real signal for it exists (e.g. an extractor flagging it directly, or a human deciding it during manual review).

**`reconcile()` matches line items across extractors by normalized description, not list position.** An early version aligned each extractor's line items purely by index — item 1 vs. item 1, item 2 vs. item 2. The team rejected this on review. Real extractors won't reliably return items in the same order or count; position-only matching would misreconcile items that actually agree (different order) or falsely agree on items that are actually different (same position, different item). `reconcile()` now groups items across extractors by `description.strip().casefold()` — items sharing a normalized description are treated as the same item and reconciled per-field; a description appearing in only some extractors' lists produces a `missing_line_item` row for the extractors missing it, naming the position (see below) and the extractor that failed to produce it. An item produced by only one extractor, with no other extractor even attempting a match, passes through unresolved with no review row — the same as a single-extractor result for a receipt-level field. This is still a simplification (exact description match, not fuzzy/semantic matching), but it is meaningfully closer to how real extractor disagreement behaves than positional alignment.

**Line-item review rows record their position via `extractor_notes`, since `line_item_id` can't be set pre-Load.** A review row for a line-item-level disagreement has no real `line_item_id` to attach at reconcile-time — `LineItem` ids and `line_order` are only assigned later, in `shape()`. Without any positional information, a person resolving several line-item review rows on a multi-item receipt has no way to tell which item each row is about. The team considered leaving `line_item_id=None` with no other signal (rejected — a real usability gap) and restructuring the pipeline to shape line items before reconciling them (rejected — diverges from the design doc's stated `reconcile → validate → shape → emit` order for no strong reason). Settled on writing the item's 1-indexed position (e.g. `"line item 2"`) into `extractor_notes`, matching the same indexing `shape()` later uses for `line_order`. `line_item_id` itself stays `None` at this stage.

## Tooling (build phase)

**uv, not poetry or plain pip.** Poetry is more established but slower, and it has its own `pyproject.toml` conventions to learn. Plain pip with `requirements.txt` has no real lockfile, so dependency versions can drift silently between installs. uv does venv, install, and lockfile as one fast tool. The team chose it for the fewest new concepts to learn on a from-scratch Python project.

**`vela-core`'s JSON Schema: vendored via git submodule.** Not a manual copy-and-sync script. Not a build-time fetch. A manual copy is the most self-contained option at runtime, needing no network access to build. But the pin exists only in human memory. Nothing stops the copy from silently drifting from `vela-core`, and nothing records which commit it came from. A build-time fetch is the least self-contained, since every build needs live network access to `vela-core`. A git submodule is the conventional git-native mechanism for exactly this situation. It gives a pinned, trackable snapshot of another repo's content, with the version relationship enforced by git rather than memory.

**Both `respx` and a standalone FastAPI mock app for `vela-api`, not `respx` alone.** `respx` is necessary either way. It is what gates fast, isolated automated tests. But it only exists inside a `pytest` run. It can't be pointed at manually. The standalone app costs more to build but lets the whole pipeline be run and inspected end-to-end before `vela-api` exists for real.

**`pre-commit` + `ruff`: matching `vela-core`'s convention, not skipping local enforcement.** `vela-core` runs eslint and prettier on staged files before every commit via Husky, with no CI. `vela-etl` has no reason to diverge from that established cross-repo convention just because the language differs. `pre-commit` + `ruff` plays the same role — lint and format, enforced before a commit lands — using Python-native tooling.

**`poethepoet` for named commands, not `[tool.uv.scripts]`.** The original plan assumed `uv` had an npm-script equivalent, configured directly in `pyproject.toml`. It does not. `uv run <name>` only runs an arbitrary one-off command, not a named task from config. `poethepoet` (`poe`) fills that gap. It is a plain PyPI dev dependency, configured entirely in `pyproject.toml`'s `[tool.poe.tasks]`, invoked as `uv run poe <task>`. The team rejected a Makefile or a Taskfile (go-task) for the same role. Both add a machine-level tool dependency outside Python's own package management. The goal was a setup that runs on any machine with `uv` already installed, nothing more.

The `src/` wrapper directory stays regardless of that naming choice. It is a separate, standard Python convention. It stops tests from accidentally importing an uninstalled local copy of the package instead of the installed one. `pyproject.toml`'s `[tool.uv.build-backend] module-name = "etl"` setting points the build backend at `src/etl/`.
