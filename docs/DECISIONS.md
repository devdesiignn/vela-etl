# Engineering Decisions

A running log of the non-obvious choices made building this repo, and why. Design/architecture reasoning lives in [`docs/design/DESIGN-V3.md`](./design/DESIGN-V3.md). This log covers the choices that had a real rejected alternative worth recording.

## Language

**Python for the whole pipeline (Extract, Transform, Load), not TypeScript.** TypeScript was the original draft assumption. The team made it before it worked out Extract's real requirements. The team reversed this once it became clear Extract carries the pipeline's actual complexity and compute cost: OCR, vision-LLM calls, per-vendor adapters. Python's OCR/ML ecosystem is native and mature there — EasyOCR, PaddleOCR, docTR, and `pytesseract` all run in-process. The TypeScript equivalents are thin or nonexistent and would need a separate Python service anyway. Once Extract needs Python, keeping Transform and Load in the same language avoids a cross-language boundary for stages that don't need one. Neither stage has any real technical pull toward TypeScript.

## Tooling

**`gen:types` runs `datamodel-codegen` with `--use-annotated`, not its default `confloat`/`constr`-style output.** By default, `datamodel-codegen`'s `pydantic_v2.BaseModel` output uses Pydantic's `confloat(ge=0.0, le=1.0)`-style wrapper functions for constrained fields (e.g. `ExtractionReview.confidence_score`). Pydantic's own docs mark these as discouraged and headed for deprecation in Pydantic 3.0. A function that returns a type doesn't play well with static analysis. `datamodel-codegen` (validated on the installed 0.80.0) already supports `--use-annotated` (which also enables `--field-constraints`), producing Pydantic's own recommended `Annotated[float, Field(ge=0.0, le=1.0)]` form instead. The team added it to `gen:types` in `pyproject.toml`. Every regeneration then stays on the non-deprecated pattern. This includes the standing per-session submodule-pin-update flow. The team did not wait for the warning to become a hard break.

## Architecture

**No direct database connection to `vela-core`, ever.** Originally the team assumed `vela-etl` would connect directly to Postgres. `vela-core` looked like schema and migrations only, not a running service. The team reversed this once the platform's write-path rule became explicit. `vela-api` is the only service with a direct connection to `vela-core`. `vela-etl` has no DB driver and no DB credentials. It calls `vela-api` over HTTP instead.

**Contract with `vela-api` is two separate things: data shape (JSON Schema) and endpoint shape (OpenAPI).** The team considered generating types from an OpenAPI spec directly. This is the way a typical REST client generator would work. Rejected. The data types already come from `vela-core`'s JSON Schema via `datamodel-code-generator`, independent of anything `vela-api` does. An OpenAPI spec, if `vela-api` ever publishes one, only ever describes the URL, method, and wrapper around that same data. There is nothing left for a second code-generation step to produce. This also means `vela-etl` never needs to know or mirror any tooling choice made on `vela-api`'s side.

**`vela-api`'s write contract: one combined-payload endpoint, not per-table endpoints.** The team considered `POST /receipts`, `POST /line-items`, and `POST /extraction-reviews` as three separate calls, more conventionally REST-ish. Rejected in favor of a single POST carrying the whole shaped receipt with nested line_items and reviews, written atomically. Reasoning: `vela-etl`'s Emit step already bundles all three into one unit. Per-table endpoints would mean re-splitting output on the way out for no benefit. Per-table calls also risk partial-write states — receipt written, line_items call fails, review call never happens — that a combined endpoint avoids by construction. This is `vela-etl`'s stated expectation handed to `vela-api`, not a guarantee of `vela-api`'s actual implementation.

**Both `vela-etl` and `vela-api` validate against `vela-core`'s JSON Schema — not just one side.** The team considered leaving validation to `vela-api` alone. It is the actual enforcement point and the single source of truth either way. The team rejected purity for practicality. `vela-etl` validates first, so a malformed payload fails fast with a useful local error during development, before a request ever leaves the pipeline. `vela-api` re-validates on receipt regardless, since it can't fully trust every caller, especially once other clients might exist. `vela-etl`'s validation is an optimization, never the enforcement mechanism.

## Privacy

**No anonymization or redaction: validated, not left open.** v1 flagged two fields as needing validation: `receipts.customer_name` and `extras`. They needed to never hold a third party's personal data. Validated: this is a local project that processes only the project owner's own receipts, with no third-party exposure path. The decision stands as data minimization, meaning extract only what the schema defines, rather than redaction. This is consistent with the platform-wide privacy principle. If the team ever needs reversible redaction, field-level (not whole-row) encryption is the fallback design. The key stays separate from the data. Decryption is a permissioned, logged action.

## Extraction

**Extractors are a plain list behind one shared interface, not a "one extractor vs. many, with a special fallback case" branch.** The team considered a different model: a primary extractor plus an explicit fallback path. If the primary extractor is low-confidence, it would call a named backup. Rejected. Reconciliation only ever sees a results list of length 1 or N. It never knows or asks how many extractors ran, or why. This makes "run two extractors always" and "run one, conditionally fall back to a second" the exact same code path downstream. Adding a new vendor is purely additive, meaning one adapter and one config entry, with zero changes to orchestration or reconciliation.

**Total-failure `ExtractionReview` shape: resolved upstream in `vela-core` commit `1619173`.** DESIGN-V3.md line 87 says a total extraction failure returns an `ExtractionReview`-shaped row directly. A total failure means an illegible image or an API error, with no candidate at all. The line cites `flagged_reason: "illegible"` as the example. That example didn't hold up against `vela-core`'s actual contract at the time. `field_name` only documented three cases: a real column name, `"line_item"`, and `"missing_line_item"`. None of the three fit the case where the extractor produced nothing at all. `vela-core`'s seed data also showed a narrow meaning for `illegible` itself. It meant one field or character was not readable, not that the whole receipt failed. `vela-etl` used `field_name="receipt"` as a provisional local placeholder. Meanwhile the team raised the case with `vela-core`.

`vela-core` resolved it in `1619173` (`feat(schema): add extraction_failed sentinel for total extraction failures`). It added a fourth `field_name` sentinel, `"receipt"`. It paired that sentinel with a new `flagged_reason` enum value, `"extraction_failed"`. The two always appear together, so either field alone identifies the case. `line_item_id`/`extracted_value` stay null, matching the existing `"missing_line_item"` pattern. The team bumped `vela-etl`'s submodule pin to `1619173` and regenerated types (`uv run poe submodule:update` + `gen:types`). `tests/test_extract.py`'s `_TotalFailureExtractor` now constructs `field_name="receipt"` + `flagged_reason=FlaggedReason.extraction_failed`. This is the real, schema-backed case, not a placeholder.

**Phase 5's two real adapters: one cloud vendor, one hand-rolled OCR parser, not two of the same kind.** The team considered two other pairings first. One was two OCR adapters, e.g. `pytesseract` plus EasyOCR. The other was two cloud vendors, e.g. Azure plus AWS Textract. The team rejected both. This phase must prove the `Extractor` Protocol holds at both ends of the adapter-effort spectrum, per `docs/IMPLEMENTATION-PLAN.md`. Two OCR adapters would prove only the hard end, twice. Two cloud vendors would prove only the easy end, twice. One of each covers both extremes with the fewest adapters. Azure Document Intelligence covers the receipt-shaped, low-effort case. RapidOCR covers the raw-text, hand-mapped case. The remaining adapters (EasyOCR, PaddleOCR, docTR, vision-LLMs) stay deferred to Phase 7.

**The OCR adapter's raw-text mapping: hand-written regex and heuristics, not a third-party receipt-parsing library.** The team considered a ready-made library. Such a library already classifies OCR text lines into store, date, total, and line-item fields. Such a library would have cut down on custom code. The team rejected this for this phase. A third-party parser's internal logic is opaque. Its maintenance status is also unknown. Using one would also defeat this adapter's actual purpose. This adapter must prove the `Extractor` Protocol holds even at the fully-manual end of the effort spectrum. There, the pipeline author writes the mapping logic directly. This follows `docs/IMPLEMENTATION-PLAN.md`'s Phase 5 framing. The hand-written parser lives in `src/etl/extract/adapters/ocr_text_parser.py`. If it turns out too brittle against real receipt layout diversity, the pipeline's own `extraction_reviews` rate will show it. That evidence is the right signal to revisit a library, not a decision made ahead of it.

**Azure's `Items[]` sometimes omits `Price` (unit price) even when `Quantity` and `TotalPrice` are both present.** The team validated this against a real F0 endpoint response. The documented schema alone did not show it. Defaulting the missing `unit_price` to `0.0` would silently produce a wrong value, not just a missing one. A valid, nonzero `line_total` next to a `unit_price` of exactly `0.0` looks like clean data, not a gap. The team fixed this in `azure_document_intelligence_adapter.py`'s `_extract_line_items`. When `Price` is absent but `Quantity` and `TotalPrice` are both present and `Quantity != 0`, the adapter derives `unit_price` as `round(TotalPrice / Quantity, 2)`. It gives this derived value its own confidence score, `_DERIVED_UNIT_PRICE_CONFIDENCE = 0.6`, the same tier `RapidOcrAdapter` uses for its own derived confidence. It does not reuse Azure's native confidence for `TotalPrice`, since Azure never reported a unit price at all.

**Azure's `prebuilt-receipt` model has no invoice or transaction-ref field in its schema at all.** The field is structurally absent, not just often missing. That concept belongs to `prebuilt-invoice`, a different Azure model. The team validated the absence against a real response, not just the documented schema. Transform's `shape()` computes `content_hash` from store, transaction_ref, date, and total. Without a real ref, this adapter would always report an empty `transaction_ref`. `content_hash` would then collide across two distinct receipts that share a store, date, and total. The two receipts would still differ in what the shopper actually bought. Fix: `_synthesize_transaction_ref` builds a deterministic ref from a SHA-256 hash of each line item's description, quantity, and line_total. This keeps the ref stable for the same physical receipt across re-runs. The ref still varies whenever the actual purchase differs. The team also considered flagging this synthesized value for human review: `field_name="transaction_ref"`, low confidence. A reviewer would then know it isn't vendor-verified. The team rejected this for this adapter. `reconcile()` resolves a single extractor's value silently whenever nothing else disagrees with it. `validate()`'s required-field rule only catches an empty or null `transaction_ref`, not a synthetic-but-present one. Surfacing this would need a new rule in Transform, out of scope for an Extract-adapter change. This fix solves the `content_hash` collision only. Review-visibility for synthesized fields, if the team wants it later, is a separate, deliberate Transform change.

**A partial extraction is a review row, not a success with a coerced value.** `CandidateReceipt.total` is non-nullable. The RapidOCR adapter therefore coerced a missing total to `0.0` and reported the extraction as a success. The team validated the cost against all 28 real sample receipts. 14 of 28 shipped wrong data that `vela-api` would have accepted as valid. One of them carried 16 line items against a `0.0` total. The team considered leaving the coercion in place and letting Transform's `validate()` catch it downstream. The team rejected this. A `0.0` total is indistinguishable from a real zero-value receipt once it leaves the adapter, so no downstream rule can recover the difference. `extract()` now routes three cases to a total-failure `ExtractionReview` instead. The first is a missing total with line items present. The second is line items absent with a total present. The third is a total that parsed as literal `0.00` with line items present. The third case is a separate code path from the first, since an `is None` test never sees a parsed zero. These three gates detect an absent value, never a partial one. A later entry below adds the reconciliation gate that covers the partial case.

**Extraction is not safe to run concurrently across processes without a cap on OCR thread pools.** The team found this by accident. It was during a sweep of the real sample receipts. Nine concurrent adapter processes produced 22 spurious `Unknown C++ exception from OpenCV code` failures. One more process silently extracted nothing and still exited with status 0. The same receipts pass cleanly when run one at a time in a single process. The cause is OpenCV and ONNX Runtime thread-pool oversubscription: each process sizes its pools to the full core count. Memory is not the constraint. A full serial run holds a stable working set with no growth across receipts. `OMP_NUM_THREADS=1` and `OPENCV_NUM_THREADS=1`, set before the import of `cv2` and `onnxruntime`, would likely make parallel extraction safe. The team has not tested this. Any future work that extracts several receipts in parallel must validate this first. The failure mode includes silent no-ops, not just visible crashes.

**Line items that do not sum to the total mean a partial read, not a success.** The three gates above detect an absent field. None detects a parse that found 1 of 5 line items. Nothing on a receipt states how many items to expect. Arithmetic is the only available signal. `extract()` now rejects a parse whose line items do not sum to the receipt total, within one cent. Tax and discount adjust the expected sum, since both legitimately break the identity. No receipt in the 28-photo sample carries either field, so the team reasoned that branch from the schema rather than from a real photo. Measuring the sums also exposed a second bug the team had not looked for. Payment lines parsed as purchased items. A `CASH 8,800.00` row and a `Net Totnl 9,550.00` row each duplicated the receipt total as an extra line item. That is why several receipts summed to an exact multiple of their total. `_PAYMENT_LINE` now excludes those lines from item parsing.

**A sideways photo earns a retry at the three quarter turns, rather than a column-detection rewrite.** One real receipt extracted nothing. An earlier note recorded it as a multi-column layout that needed x-position clustering. Dumping both OCR passes showed a simpler cause. The photo is sideways. EXIF orientation does not help, because a receipt photographed rotated on a flat surface carries no orientation tag. The text reads fine. The turned box geometry then makes `_group_boxes_into_lines()` read across the receipt instead of down it. The team considered the column-clustering rewrite first and rejected it. That approach targets a diagnosis the image data contradicts. It would also mean a rewrite of the one function every receipt depends on. Instead `extract()` measures the grouped output. Upright receipts give 18 to 40 lines averaging 18 to 28 characters. Sideways ones give 4 to 9 lines averaging 59 to 90. On that signature it tries 90, 180 and 270 degrees. It appends each parse as another candidate. This is additive. A rotation only adds a candidate, and the existing best-parse selection still decides. A rotation that reads worse cannot regress a receipt that already worked.

## Transform

**`shape()`'s extras split: introspect `Receipt.model_fields` at runtime, not a hardcoded field list.** The team considered an explicit set of recognized column names, written directly in `shape.py`. That set would stay independent of the generated `Receipt` model. Rejected. `datamodel-code-generator` generates `Receipt` from `vela-core`'s vendored JSON Schema (`uv run poe gen:types`). A hardcoded list would silently drift out of sync at the next schema change and regeneration. It would need a second manual edit that somebody can easily forget. Runtime introspection of `Receipt.model_fields` makes any resolved key that matches a real field name on the generated model a column. Everything else goes into `Receipt.extras`. By definition, that is anything the schema does not recognize. A schema change plus a `gen:types` regen takes effect automatically, with zero code changes in `shape.py`. `LineItem` and `Store` need no equivalent split. Neither has an `extras` field in the schema. Their candidate types (`CandidateLineItem`/`CandidateStore`) only ever define real schema fields in the first place.

**`validate()`'s derived confidence score scales with the size of the arithmetic mismatch, not a flat value.** An early version used one fixed score. It applied that score to every self-caught inconsistency. That score was `confidence_score=0.0`. One such inconsistency is `quantity * unit_price != line_total`. The team rejected this on review. A total off by a rounding-sized amount (1%) is a meaningfully different signal than one off by 50%+. A single score for both throws that signal away. `validate()` now computes a relative error (`abs(actual - expected) / denominator`). It maps that error to `1.0 - relative_error`, with a floor of `0.0` and a cap of `0.99`. A flagged row can thus approach full confidence but never reach it. A missing required field has no distance to measure, so it keeps the flat `0.0`. The scaling only applies to arithmetic mismatches. They are the only case with a meaningful distance to measure. **Follow-up fix, same review round**: the initial version divided by `expected` directly. A small absolute gap on a small total then computed as a huge relative error. For example, a total of 1.00 that is off by 0.05 gives 95%. The formula clamped that to the same 0.0 score as a receipt that was wildly, unambiguously wrong. The two became indistinguishable, even though the absolute gap was currency-scale trivial. A first fix floored the denominator at a hardcoded `10.0`. That number itself carried a currency and magnitude assumption with no real basis. What counts as small varies by currency and receipt scale. **Final fix**: the formula no longer reasons about the receipt's total's scale at all. An absolute gap within `_NEGLIGIBLE_GAP_MULTIPLE` (5) multiples of `_TOLERANCE` counts as negligible and scores `0.99`, regardless of `expected`'s size. `_TOLERANCE` is the same 0.01 unit the pass/fail arithmetic test already uses. Only once the gap exceeds that multiple does relative error start to degrade the score further. This ties the meaning of a small gap to the same currency-unit-agnostic tolerance the file already defines, instead of an arbitrary absolute floor.

**`reconcile()` matches line items across extractors one item at a time against open groups, not by a precomputed `(description, occurrence)` key.** Two versions preceded this one. Review found a real bug in each. First version: grouped purely by normalized description, so the same product listed twice on one receipt (e.g. two "Coca-Cola 500ml" lines) had its second occurrence silently overwrite the first — a real bug that needed a fix, not just a documented limitation. Second version: the team fixed that by keying groups on `(normalized_description, occurrence_index)`. This counts each extractor's Nth occurrence of an exact description string. It introduced a subtler bug. Occurrence-counting used the *exact* string as its key. One extractor could spell a duplicate item's two occurrences inconsistently, for example "Paracetamol" then "Paracetmol", a typo on the second. The two occurrences then became two entirely different description keys with independent occurrence counters. That broke the correspondence between extractors' Nth occurrences. **Current version**: the code assigns each item to a group one at a time. It finds the best still-open group, meaning a group this extractor has not already filled. It prefers an exact normalized-description match, falls back to a fuzzy match, and opens a new group only if neither exists. Matching then holds regardless of *why* one extractor's two occurrences of the same item look different. The reason can be a typo, or a real duplicate with no typo at all. Group assignment asks whether a compatible open group exists. It never uses a description string as a literal dictionary key.

**`reconcile()` falls back to fuzzy description matching for line items that don't match exactly.** It uses stdlib `difflib.SequenceMatcher`. Exact-match-only matching, after case and whitespace normalization, does not tolerate small OCR-style typos between extractors. One example is "Paracetmol 500mg" against "Paracetamol 500mg". Such a pair would otherwise become two entirely different items, rather than one item with a field-level disagreement. The user validated this. The team added a conservative similarity threshold, `_DESCRIPTION_SIMILARITY_THRESHOLD = 0.9`. It is high enough that short, genuinely different words stay below it and never merge. One example is "Milk" against "Mild", one character apart but different products. The threshold still catches small single-character-class differences. Fuzzy matching only ever applies as a fallback when no exact-match open group exists. It never lets one extractor fill more than one slot in the same group. The group-matching entry above shows how this composes with duplicate items. This is still an approximation, with no semantic understanding of product names. This entry records it as such. It is not a complete solution to real-world OCR noise.

**A single-extractor line item, among 2+ total extractors, earns a `low_confidence` flag.** That flag sits on top of the `missing_line_item` rows the item already has. Previously `reconcile()` accepted such an item into `resolved_items` with no review flag at all. The absence of the other extractors already produces `missing_line_item` rows for them. The item's own existence is therefore in dispute. Even so, the code trusted its field values like those of an item every present extractor agreed on. Fixed: when more than one extractor ran in total and only one produced this item, `reconcile()` adds a `flagged_reason="low_confidence"` row. The row uses `field_name="line_item"`. That reuses the same sentinel the design doc defines for a whole item that is wrong. This case is closely related but distinct. The item lacks a second extractor's agreement. It is not necessarily wrong. This does **not** apply when only one extractor ran in total. That is the ordinary single-extractor pass-through case. Nothing else exists to dispute the item.

**`_reconcile_line_items` keys missing and present extractor accounting by list index, never by `extractor_source` name.** An earlier version built a `set` of `source` strings. The set told it which extractors were present or absent for a given line-item group. This silently breaks if two `ExtractionResult`s in the list share the same `source` name, for example the same extractor run twice. The set collapses the two into one entry. An extractor that genuinely produced nothing can then hide behind another entry of the same name that did produce something. The fix tracks `result_index` throughout. That index is the position in the `results` list and is always unique. The code resolves to the `source` string only when it constructs each `ExtractionReview` row.

**`shape()` constructs `Receipt` before computing `content_hash` from its fields, not the other way around.** The original order computed `content_hash` first, from raw dict values that `columns.get(...)` returned. It constructed `Receipt` afterward. A required field could be missing from `columns`, for example left unresolved by `reconcile()`. The hash function then received `None` and silently hashed the literal string `"None"`. That produced a valid-looking hash for a receipt that was about to fail construction anyway. It did not raise immediately. The fix constructs `Receipt` first, with an empty placeholder `content_hash`. Pydantic's required-field validation then runs and raises before any hashing happens. The code then computes the real hash from the validated `receipt` instance's own fields and assigns it.

**`reconcile()` raises rather than silently truncating when `Candidate.line_items` and `Confidence.line_items` mismatch in length.** `extract/types.py` documents `Confidence.line_items` as positionally aligned with `Candidate.line_items`. `ExtractionResult`'s own construction never enforces that the two lists are the same length. An earlier version zipped them with `strict=False`. A malformed `ExtractionResult` with mismatched lengths, from an orchestrator or extractor bug, would then silently drop a real line item from reconciliation. There would be no error and no review row. The fix makes `_group_line_items_by_description` compare the lengths per extractor before it zips. It raises `ValueError` with a clear message that names the offending `source`. It no longer trusts `zip`'s silent-truncation default. A length mismatch signals that something upstream built the `ExtractionResult` itself incorrectly — `reconcile()` should never paper over that.

**`shape()`'s extras split matches resolved keys against declared field aliases as well as attribute names, not attribute names alone.** `Receipt.model_fields` gives Python attribute names. It does not automatically include any alias a field declares. For example, `datamodel-code-generator` could regenerate `Receipt` with a camelCase JSON alias mapped to a snake_case attribute. `vela-core`'s JSON Schema could introduce such an alias at any future regen. A match on attribute names alone would then silently misroute an alias-spelled resolved key into `extras` instead of the real column, with no error. That gap would only surface once such an alias existed. By then the wrong routing would already be happening silently. Fixed defensively: the known-fields set now also includes each field's `info.alias` and `info.validation_alias` when declared. `Receipt` declares no aliases today, so this has no behavioral effect on the current schema. The routing holds without a code change if that changes on a future regen.

**Verified non-issue, external review**: an external review claimed a type-coercion risk in `validate()`'s arithmetic. The claim was that `quantity * unit_price` assumes numeric types without a coercion guard. The team compared the claim against the actual data flow, and it does not hold. Every value `validate()` operates on originates from `reconcile()`'s output. That output always comes from a `CandidateLineItem` instance, where `extract/types.py` types `quantity`, `unit_price`, and `line_total` as `float`. It arrives either via `.model_dump()` for single-extractor items, or via `getattr()` on the same typed instance for per-field-reconciled items. No path introduces a raw, unvalidated string into `resolved["line_items"]`. The team applied no fix. This entry records the finding so nobody drops it silently without explanation.

**`shape()` filters `id`/`receipt_id`/`line_order` out of `item_fields` before it constructs each `LineItem`.** It does not trust `CandidateLineItem` to never produce those keys. `reconcile()`'s single-extractor pass-through path (`resolved_items.append(item.model_dump())`) dumps the full `CandidateLineItem` model. It does not dump only the fields `shape()` expects to spread. `CandidateLineItem` doesn't declare `id`/`receipt_id`/`line_order` today. `LineItem(id=..., receipt_id=..., line_order=index, **item_fields)` therefore cannot collide currently. That safety depended entirely on an assumption about a type `shape()` doesn't own and doesn't control. That type is Phase 2's `CandidateLineItem`, which is still evolving. That schema could grow to include one of those names. This is plausible, since `LineItem` itself has all three. The unfiltered spread would then raise `TypeError: got multiple values for keyword argument` on every affected receipt, with no warning beforehand. The fix matches the receipt-level known-fields split. `shape()` explicitly excludes `{"id", "receipt_id", "line_order"}` from `item_fields` before it spreads them. Its own explicit assignments then always win, regardless of what `item_fields` holds. `LineItem` has no `extras` field to route excess keys into (unlike `Receipt`), so filtering (not redirecting) is the only option here.

**`validate()` flags a receipt that resolves to a nonzero total with zero line items.** The sum validation (`line items total == receipt total`) previously skipped entirely when `line_items` was empty. There was nothing to sum. But a receipt with a real total and zero items is almost certainly a total extraction failure, where the adapter missed every item. It is not a legitimately empty receipt, and it deserves a review row. Fixed: an empty `line_items` list with a nonzero `total` now produces a `field_name="missing_line_item"` validation-failure row. A `total` of `0.0` (a genuinely zero-value/voided transaction) is not flagged, since that combination isn't inherently suspicious.

**Transform's validator: pydantic only, not `jsonschema` as well.** The design doc's tool inventory lists `pydantic` or `jsonschema` for validation against `vela-core`'s JSON Schema. It allows both, if this log records why. The team considered running `jsonschema` against the vendored `.schema.json` files directly, on top of pydantic, as a literal belt-and-suspenders validation. The team rejected this as redundant. `datamodel-code-generator` produces the generated types (`src/etl/types/*_schema.py`) directly from those same vendored schema files. Construction of a `Receipt`/`LineItem`/`Store`/`ExtractionReview` instance from shaped data already enforces the schema's required fields, types, and constraints. The model literally is that schema's Python representation. A second `jsonschema` run against the same source files would duplicate the exact same validation through a second code path. It would gain no independent guarantee. Both readers trace back to one source of truth. `shape()`'s construction of `Store`/`Receipt`/`LineItem` is therefore documented as the pre-Load re-validation step, not a separate stage.

**`shape()` requires fully-resolved input. it does not validate unresolved conflicts itself.** The team considered a defensive step inside `shape()`. It would validate `reconcile()`'s review list for unresolved receipt/store-level conflicts before it builds `Store`/`Receipt`/`LineItem`. It would then skip or fail gracefully if any exist. Rejected for `shape()` itself. `shape()` stays a pure function that trusts its input is already resolved. This matches the design doc's stated pipeline order (`reconcile → validate → shape → emit`). Conflict detection is `reconcile()`'s own output, the review list. `shape()` should not re-derive it. Validated by testing. `reconcile()` can leave a required field such as `total` unresolved because the extractors disagree. Fed such a receipt, `shape()` makes pydantic raise `ValidationError` during `Receipt` construction. The field is simply missing from the resolved dict. The team treats this as right, not as a gap to patch inside `shape()`. A receipt with a disagreed-upon required field must never reach Load. The gap that does need closing is in the caller. **Phase 6's end-to-end wiring must validate `reconcile()`'s review list for unresolved receipt/store-level conflicts before it calls `shape()`.** It must then route that receipt to review. It must not call `shape()` and catch the resulting error. It must not call `shape()` and catch the resulting error.

**`reconcile()` never infers "the whole line item is wrong" (`field_name="line_item"` sentinel) from how many fields mismatch.** An early version guessed this. If 2+ fields disagreed on the same aligned line item across extractors, it collapsed those into one `field_name="line_item"` row. It did not emit several per-field rows. The team rejected this on review. It was an invented threshold with no basis in the design doc. It also hides which specific fields disagreed from whoever resolves the review. `reconcile()` now only ever emits per-field rows for line-item disagreements, same as receipt/store-level fields. `field_name="line_item"` (whole item wrong) and `field_name="missing_line_item"` (item missed entirely) stay real cases. This follows `CLAUDE.md`'s "shared data contract" rules. But `reconcile()` does not try to detect a whole wrong item on its own. That stays out of scope for Transform until a real signal for it exists. Such a signal could be an extractor that flags it directly, or a human who decides it during manual review.

**`reconcile()` matches line items across extractors by normalized description, not list position.** An early version aligned each extractor's line items purely by index. It matched item 1 against item 1, and item 2 against item 2. The team rejected this on review. Real extractors won't reliably return items in the same order or count. Position-only matching would misreconcile items that actually agree but arrive in a different order. It would also falsely agree on items that are actually different but share a position. `reconcile()` now groups items across extractors by `description.strip().casefold()`. Items that share a normalized description become the same item, and it reconciles them per-field. A description that appears in only some extractors' lists produces a `missing_line_item` row for each extractor that lacks it. The row names the position (see below) and the extractor that failed to produce it. An item can come from only one extractor, with no other extractor even attempting a match. It then passes through unresolved with no review row. This matches a single-extractor result for a receipt-level field. This is still a simplification, since it uses exact description match rather than fuzzy or semantic matching. Even so, it sits meaningfully closer to real extractor disagreement than positional alignment.

**Line-item review rows record their position via `extractor_notes`, since `line_item_id` can't be set pre-Load.** Such a row has no real `line_item_id` to attach at reconcile-time. `shape()` only assigns `LineItem` ids and `line_order` later. Without any positional information, a person can face several line-item review rows on a multi-item receipt. That person then has no way to tell which item each row is about. The team considered `line_item_id=None` with no other signal. It rejected that as a real usability gap. The team also considered a restructured pipeline that shapes line items before it reconciles them. It rejected that too, since it diverges from the design doc's stated `reconcile → validate → shape → emit` order for no strong reason. The team settled on the item's 1-indexed position, written into `extractor_notes`, for example `"line item 2"`. This matches the same indexing `shape()` later uses for `line_order`. `line_item_id` itself stays `None` at this stage.

## Tooling (build phase)

**uv, not poetry or plain pip.** Poetry is more established but slower, and it has its own `pyproject.toml` conventions to learn. Plain pip with `requirements.txt` has no real lockfile, so dependency versions can drift silently between installs. uv does venv, install, and lockfile as one fast tool. The team chose it for the fewest new concepts to learn on a from-scratch Python project.

**`vela-core`'s JSON Schema: vendored via git submodule.** Not a manual copy-and-sync script. Not a build-time fetch. A manual copy is the most self-contained option at runtime, needing no network access to build. But the pin exists only in human memory. Nothing stops the copy from silently drifting from `vela-core`, and nothing records which commit it came from. A build-time fetch is the least self-contained, since every build needs live network access to `vela-core`. A git submodule is the conventional git-native mechanism for exactly this situation. It gives a pinned, trackable snapshot of another repo's content, with the version relationship enforced by git rather than memory.

**Both `respx` and a standalone FastAPI mock app for `vela-api`, not `respx` alone.** `respx` is necessary either way. It is what gates fast, isolated automated tests. But it only exists inside a `pytest` run. It can't be pointed at manually. The standalone app costs more to build but lets the whole pipeline be run and inspected end-to-end before `vela-api` exists for real.

**`pre-commit` + `ruff`: matching `vela-core`'s convention, not skipping local enforcement.** `vela-core` runs eslint and prettier on staged files before every commit via Husky, with no CI. `vela-etl` has no reason to diverge from that established cross-repo convention just because the language differs. `pre-commit` + `ruff` plays the same role — lint and format, enforced before a commit lands — using Python-native tooling.

**`poethepoet` for named commands, not `[tool.uv.scripts]`.** The original plan assumed `uv` had an npm-script equivalent, configured directly in `pyproject.toml`. It does not. `uv run <name>` only runs an arbitrary one-off command, not a named task from config. `poethepoet` (`poe`) fills that gap. It is a plain PyPI dev dependency, configured entirely in `pyproject.toml`'s `[tool.poe.tasks]`, invoked as `uv run poe <task>`. The team rejected a Makefile or a Taskfile (go-task) for the same role. Both add a machine-level tool dependency outside Python's own package management. The goal was a setup that runs on any machine with `uv` already installed, nothing more.

The `src/` wrapper directory stays regardless of that naming choice. It is a separate, standard Python convention. It stops tests from accidentally importing an uninstalled local copy of the package instead of the installed one. `pyproject.toml`'s `[tool.uv.build-backend] module-name = "etl"` setting points the build backend at `src/etl/`.
